# BatteryTray 2.0.0

这次跳到大版本，是因为设备读取这条路换了个底：**2.4G 和蓝牙设备的连接判断
都重写了**，另外把几个长期潜伏的问题一起修掉。

## 一、2.4G 鼠标读不到电量（已修）

诊断报告里这一行就是症结：

```
失败的驱动:
    asus: Argument 'path' has incorrect type (expected bytes, got str)
```

驱动把 HID 接口的路径当普通文字又传回给 HID 库，那个调用要的是字节串，
抛的是 `TypeError` —— 而驱动只捕获 `OSError`，于是整个驱动停摆：接收器在，
电量一次都没查过。同样的写法在罗技、ATK/VXE 等 2.4G 品牌驱动里也有。

现在统一走 `hidsupport.open_interface()`，路径保持系统给的原始字节。

## 二、蓝牙设备被误判离线（已修）

判断「还在不在」时，程序把注册表里的 `LastConnected` 当成了设备的最近活动。
可这个时间戳**只在链路建立时写一次**：耳机连着放几个小时，它就一直是几个
小时前，正在用的耳机被判成离线、电量被隐藏。

现在只有设备节点自己的活动戳算活动；注册表时间戳只能证明「设备在」，不能
证明「设备不在」。

## 三、蓝牙无线电查询从来没成功过（已修）

这一条是上面那个误判的根子。程序本来有个最权威的依据 —— 直接问蓝牙无线电
「哪些链路现在是通的」。可它问话用的结构体是凭记忆拼的：

| 字段 | 原来 | Windows 要的 |
|------|------|--------------|
| BOOL 标志 | 1 字节 | 4 字节 |
| hRadio | DWORD | HANDLE（64 位下 8 字节） |
| 地址 | 4 字节 | 8 字节 |
| 名字 | 124 字符 | 248 字符 |
| 时间戳 | FILETIME | SYSTEMTIME |

Windows 会核对结构体大小，对不上就一律拒绝 —— 所以这条查询每次返回空，
程序只能退回去看时间戳。现在按文档重写，补上
`BluetoothFindDeviceClose`（以前每次查询都漏一个句柄）。修好后本机实测
0.01 秒返回两个真设备。

## 四、窗口不再永远置顶

设置 / 检查更新 / 诊断 / 重命名 / 鼠标参数这些对话框，以及托盘的免边框
电量浮窗，以前一律 `-topmost`，只要开着就永远在最前面。

现在：

- 对话框不再置顶，打开时 `lift` 到前台，之后可以被别的窗口盖住
- 浮窗创建时不置顶；显示的瞬间临时置顶 80 毫秒把自己带到前台，随后立刻
  取消 —— 点托盘图标仍然会正确出现在最前面，但可以被覆盖

## 五、其他

- **托盘弹出面板的图标**：刷新时丢掉图标对象，其析构会回调 tkinter；若正好
  撞进 tkinter 自己的调用里，进程会以访问冲突结束。释放位置改成明确的。
- **诊断报告**：HID 部分补上 `usage_page` / `usage` / 接口集合，接口列表不再
  截断到 20 个（识别 2.4G 接收器就靠这些）；蓝牙部分把每个设备的时间戳全列
  出来，并改为本地时间显示（以前是 UTC，晚上九点的报告写着 13:18）。

## 验证

`verify_all.py` **285 项通过**，本轮新增 12 项：

- 用「只要收到字符串就报错」的假 HID 接口模拟真实 ctypes：ASUS / 罗技 /
  2.4G 品牌三个驱动，路径必须以字节传下去，并且设备要被真正读出来
- 耳机的真实数字：电量 7 分钟前 + 注册表连接 8 小时前 + 无活动戳 → 必须算
  「在」；同样证据放到 4 天前 → 必须算「不在」
- 蓝牙结构体逐字段偏移与总大小（40 / 560 字节）
- 对话框和浮窗的 `-topmost` 必须为 0
- 诊断报告要写出 usage_page、接口集合，以及蓝牙的每一个时间戳

把驱动换回改之前的样子，这些用例的报错正是
`Argument 'path' has incorrect type (expected bytes, got str)`。
