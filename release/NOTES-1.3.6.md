# BatteryTray 1.3.6

这一版修三件事：**2.4G 鼠标读不到电量**、**连着的蓝牙耳机被当成离线**，
以及**蓝牙「链路状态」这条查询从来就没成功过**。

## 一、2.4G 鼠标：路径当成了普通文字

诊断报告里这一行说得很明白：

```
失败的驱动:
    asus: Argument 'path' has incorrect type (expected bytes, got str)
```

驱动把 HID 接口的路径当成了普通文字，又原样传回给 HID 库。那个调用要的是
**字节串**，收到字符串会抛 `TypeError` —— 而驱动只捕获 `OSError`，于是整个
ASUS 驱动直接停摆：接收器明明在（报告里能看到 `0B05:1A68 ROG KERIS
WIRELESS AIMPOINT`），却一次电量查询都没发出去。

同样的问题在**罗技**和**其他 2.4G 品牌**的驱动里也藏着，只是那台机器上没有
罗技设备，才没暴露出来。

修法：新增统一的打开入口 `hidsupport.open_interface()`，路径保持系统给的
原始字节，文字副本只用来区分接口；万一中途被转成文字，这里会再转回字节。
ASUS、罗技、ATK/VXE 等 2.4G 品牌全部改走这个入口。

## 二、蓝牙耳机：把「上次连接」当成了「最近活动」

报告里耳机是这样的：

```
HUAWEI FreeClip Hands-Free AG
    类型=headset 电量=100 连接=False
    电池上报=…（7 分钟前才报过电量）
```

判断「还在不在」时，程序把注册表里的 `LastConnected`（上次建立链路的时间）
当成了「设备最近有没有动静」的证据。可这个时间戳**只在链路建立时写一次**：
耳机连着放了几个小时，它就一直是几个小时前 —— 所以正在用的耳机被判定离线，
电量被隐藏。

修法：只有设备节点自己的活动戳才算「活动」；注册表的时间戳只能用来证明
「设备在」，不能用来证明「设备不在」。

## 三、蓝牙无线电这条查询：结构体从来就没对上过

这一条是上面那个问题的根子。程序本来有个最权威的判断依据 —— 直接问蓝牙
无线电「哪些链路现在是通的」。可它问话用的结构体是凭记忆拼的：

| 字段 | 原来 | Windows 要的 |
|------|------|--------------|
| BOOL 标志 | 1 字节 | 4 字节 |
| hRadio | DWORD | HANDLE（64 位下 8 字节） |
| 地址 | DWORD | 8 字节 |
| 名字 | 124 字符 | 248 字符 |
| 时间戳 | FILETIME | SYSTEMTIME |

Windows 会核对结构体大小，对不上就**直接拒绝**。于是这条查询每一次都返回
空，程序只好退回去看时间戳 —— 也就是第二段那个误判。

修法：按文档把 `BLUETOOTH_DEVICE_SEARCH_PARAMS` 和 `BLUETOOTH_DEVICE_INFO`
重新写对，`BluetoothFindNextDevice` 传对话柄，并补上
`BluetoothFindDeviceClose`（以前查完从不关闭，句柄一直漏）。

现在同一条查询在这台机器上 0.01 秒就带回两个真设备：

```
JBL PS3500      connected=False
WH-CH720N       connected=False
```

## 四、顺手修的两个小问题

- **托盘弹出面板的图标**：刷新时会丢掉旧的图标对象，它的析构函数会回调
  tkinter。如果这一下正好发生在 tkinter 自己的调用里，进程会直接以访问冲突
  结束（测试里偶发过）。现在图标的释放放在明确的位置，不再交给垃圾回收。
- **诊断报告**：
  - HID 部分多了 `usage_page`、`usage` 和接口集合（`MI_02&Col03`），
    接口列表也不再截断到前 20 个 —— 识别一个 2.4G 接收器就靠这些。
  - 蓝牙部分把每个设备的时间戳全列出来（电池上报、节点活动、注册表
    `LastConnected`、`LastSeen`），并且**按本地时间显示**（以前是 UTC，
    晚上九点做的报告写着 13:18，看起来像几个小时前的）。

## 验证

`verify_all.py` **282 项通过**（新增 10 项）：

- 一个「只要收到字符串就报错」的假 HID 接口，模拟真实 ctypes 的行为；
  ASUS / 罗技 / 2.4G 品牌三个驱动各一项：路径必须以字节传下去，并且设备
  要被真正读出来（85% / 60% / 55%）
- 耳机那一组用报告里的真实数字：电量 7 分钟前、注册表连接 8 小时前、
  没有活动戳 → 必须算「在」；同样的证据放成 4 天前 → 必须算「不在」
- 蓝牙结构体的字段偏移和总大小（40 / 560 字节）逐项核对
- 诊断报告要写出 usage_page、接口集合，以及蓝牙的每一个时间戳

把驱动换回改之前的样子，这些用例的报错正是
`Argument 'path' has incorrect type (expected bytes, got str)`。
